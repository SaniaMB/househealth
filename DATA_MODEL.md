# 🗄 Data Model

## Overview

HouseHealth uses a relational data model centered around users, health records, and family-based health sharing.

The model is designed to support:

- Secure user authentication
- Health metric tracking
- Family collaboration
- Care relationships
- Notifications
- Reminder scheduling
- Email verification
- Password recovery

# User

## Purpose

Represents a registered user of HouseHealth.

A user can record health metrics, participate in one or more families, receive notifications, configure reminders, and authenticate securely.

### Relationships

- One-to-Many → HealthLog
- One-to-Many → Notification
- One-to-Many → ReminderSettings
- One-to-Many → VerificationToken
- One-to-Many → PasswordResetToken
- Many-to-Many → Family (through FamilyMembership)
- Participates in CareRelationship

---

# HealthLog

## Purpose

Stores a health measurement recorded by a user.

Supported metric types include:

- Blood Pressure
- Fasting Blood Sugar
- Post-Meal Blood Sugar

Health logs power:

- Dashboard
- Trend Analysis
- PDF Reports
- Historical Charts

### Relationships

- Many-to-One → User

---

# Family

## Purpose

Represents a family group that allows members to securely share health information.

Families support multiple owners and member management.

### Relationships

- One-to-Many → FamilyMembership
- One-to-Many → FamilyInvitation
- Created by → User

---

# FamilyMembership

## Purpose

Associates users with families.

Stores family-specific roles such as ownership without modifying the User entity.

### Responsibilities

- Family membership
- Ownership status
- Join date

### Relationships

- Many-to-One → User
- Many-to-One → Family

---

# FamilyInvitation

## Purpose

Represents an invitation sent to an email address requesting the recipient to join a family.

Invitations track their lifecycle through different states.

### Invitation Status

- Pending
- Accepted
- Declined

### Relationships

- Many-to-One → Family
- Many-to-One → User (Invited By)

---

# CareRelationship

## Purpose

Represents a care relationship between family members.

Users may organize selected family members into their personal care circle for quicker access to their health information.

### Relationships

- Observer → User
- Tracked User → User

---

# ReminderSettings

## Purpose

Stores reminder preferences for individual health metrics.

Each user can configure reminder frequency and notification preferences.

Supported reminder frequencies include:

- Weekly
- Monthly
- Custom interval

### Relationships

- Many-to-One → User

---

# Notification

## Purpose

Represents notifications generated by application events.

Examples include:

- Reminder notifications
- Family invitations
- Invitation responses
- Care relationship updates

### Relationships

- Many-to-One → User

---

# VerificationToken

## Purpose

Stores secure email verification tokens generated during account registration.

Tokens are time-limited and invalidated after successful verification.

### Relationships

- Many-to-One → User

---

# PasswordResetToken

## Purpose

Stores password reset tokens used during the password recovery process.

Tokens expire after a configurable duration and may only be used once.

### Relationships

- Many-to-One → User

# Design Decisions

## FamilyMembership Join Entity

Rather than storing a `familyId` directly in the User entity, HouseHealth uses a dedicated `FamilyMembership` entity.

Benefits include:

- Supports multiple families per user
- Stores ownership information
- Records join timestamps
- Keeps User independent of family-specific logic

---

## Care Relationships

Care relationships are modeled independently from family membership.

A user must already belong to the same family before creating a care relationship, but separating these concepts allows users to organize which family members they monitor more closely.

---

## Token Entities

Email verification and password reset use dedicated token entities instead of storing tokens on the User entity.

Benefits include:

- Separation of concerns
- Token expiration support
- Independent lifecycle management
- Improved security

---

## Health Logs

All health metrics are stored in a single HealthLog entity and differentiated using metric-specific fields and enums.

This avoids unnecessary duplication while supporting multiple health metric types within a unified model.

---

# Summary

The data model emphasizes:

- Separation of concerns
- Secure authentication workflows
- Flexible family relationships
- Extensible health tracking
- Maintainable domain modeling

The design allows new health metrics and additional collaborative features to be introduced with minimal impact on the existing schema.
